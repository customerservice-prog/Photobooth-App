# Finished keepsake export and event consistency

The photo preview now prepares a 1200x1800 JPEG from the same deterministic SVG renderer used by the paper design. The guest's Share Keepsake, Download Keepsake and configured direct text/email controls use this completed file, including artwork, names, date and selected filter. Short Video and Animated GIF remain separate, unchanged media paths.

Rendering runs before the share button is enabled. The native share API is called immediately within the user's tap with a prebuilt File, not after awaiting canvas work. An export key includes the photo, configuration, monogram, design and filter; stale asynchronous results cannot replace the current file. Output is JPEG with a 2 MiB cap; quality is reduced before rejecting an oversized output. No guest image is uploaded by preparing or downloading this file. Direct delivery still uploads only after explicit recipient consent and a valid owner-paired session.

Event editing is a draft, with explicit Save and Cancel. Changing to Birthday no longer preserves a wedding title/spouse fields. Each event type keeps its own draft details; changing back restores the appropriate ones. The known old Bryan Wedding test-preset carryover is normalized only when the other event's identifying details are absent. The saved event is not overwritten until Save. Busy native/direct sending pauses the preview idle reset. Inactive recipient forms still use the existing idle reset for privacy.

Verification performed locally: 27 Node tests for draft isolation, event composition, exact-file sharing, cancellation, stale-render races, and parent/child wiring. Local Chromium ran the actual export and SVG-rendering functions on 72 combinations (18 designs x 4 filters) with a synthetic test photograph. All decoded as 1200x1800 JPEG below 2 MiB; original-center-color and grayscale checks passed, all sample SVG text bounds were on-page, and no page errors occurred. A tap harness verified transient activation reached the share function with the completed File; the native share target was stubbed and NO external message was sent. One 288x432-point, single-page PDF was rendered and visually inspected as a print-layout simulation, not a Canon driver or physical print.

The container cannot resolve the production hostname, and its browser network policy blocks HTTP navigation. The local Chromium tests therefore inject these actual source functions into an in-memory test page; they are NOT a full interactive production-page, iPad Safari, Apple share-sheet, SMS/email receipt or physical Canon test. Deployment logs must separately establish build/test/deployment success.

Provider access is separate: this change does not create Resend/Twilio credentials, enable sending flags or imply delivery. Email means Resend acceptance/receipt as described by the gateway; SMS uses a private download link. Real recipient delivery and physical SELPHY output remain unverified until tested with configured accounts and hardware. No marketing subscription is created.
